>哨兵元素：一个是防踩踏，一个是预留一个空格

>无锁的条件：1. 读是原子性的；2. W R游标，只有一个写者

可以不用哨兵，但"不用哨兵"之后，"是否还是无锁"就要看你用**哪种替代方案**了——这是两个不同维度的问题。先给结论，再展开。

---

## 一句话结论

- **能不能不用哨兵？** 能，有替代方案（加计数变量、用差值索引等）。
- **不用哨兵还是不是 SPSC？** SPSC 是"拓扑结构"（单生产者 + 单消费者），跟哨兵无关，所以**只要还是一个人写、一个人读，就仍是 SPSC**。
- **但"还是不是无锁（零竞争）"就不一定了**：哨兵方案之所以"又无锁又零竞争"，正是因为它巧妙地用"牺牲一个槽位"换来了"每个索引只有一个写者"。一旦换成别的方案，很可能破坏这一点。

---

## 环形队列区分"空/满"的几种经典做法

| 方案 | 满判定 | 空判定 | 可用容量 | 竞争情况 |
|---|---|---|---|---|
| **A. 哨兵空位**（ipc-shm 用的） | `(write+1)%N == read` | `read == write` | N-1 | **零竞争**（每个索引单写者） |
| **B. 计数变量 count** | `count == N` | `count == 0` | N | count 被两端同时写 → **有竞争** |
| **C. 差值索引**（write/read 用更大位宽，做减法） | `write - read == N` | `write - read == 0` | N | 索引仍单写者，**可零竞争**，但边界复杂 |

哨兵方案就是方案 A。你问"不用它"，通常指换成 B 或 C。

---

## 不用哨兵的两种主要做法

### 做法 B：加一个 count 计数器（最直观）

不浪费槽位，但引入一个**被生产者和消费者共同读写**的变量：生产者放一个就 `count++`，消费者取一个就 `count--`。

问题来了：这个 `count` 在共享内存里，两端都要写它。这就**破坏了 ipc-queue 的"单写者"原则**。

回顾 ipc-queue 的核心设计（`ipc-queue.h` 注释）：

```c
 * Read indexes of push_ring and pop_ring are swapped to avoid writing read
 * index in remote memory when doing pop operations.
```

这个设计让**每一个索引都只有一个写者**：

| 索引 | 唯一写者 |
|---|---|
| push_ring.write | 本地生产者 |
| push_ring.read | 本地消费者 |
| pop_ring.write | 远端生产者 |
| pop_ring.read | 远端消费者 |

所以根本不需要锁、也不需要原子操作——这就是它"无锁且零竞争"的本质。

而 `count` 变量做不到这一点：`++` 和 `--` 是"读-改-写"，两端都要碰同一个字。结果只有两条路：

- **加锁** → 已经不是无锁了；
- **用原子操作（CAS / 原子 RMW）** → 表面"无锁"，但实际上：
  - 依赖硬件的原子指令、内存屏障、缓存一致性；
  - 两端要争抢同一个 cache line，有真竞争和性能开销；
  - 在 ipc-shm 这种**异构核共享内存**（A53 / M7 / M4 / R52…）场景下，跨核原子性未必都有保证，平台依赖极强。

**所以：换成 count 方案，SPSC 拓扑没变，但"无锁、零竞争"这个性质就没了。**

### 做法 C：用差值索引（write - read）判定，不用哨兵也不浪费

这是真正的"仍然无锁、零竞争"的替代方案。做法是让 write/read 用足够大的无符号整数，靠差值判断：

- 空：`write - read == 0`
- 满：`write - read == N`（N 格全用上）

它的索引仍然满足"每个索引单写者"，所以**依然是零竞争无锁**，而且比哨兵多用一个格子。

那为什么 ipc-shm 还是选了哨兵（方案 A）而不是方案 C？原因主要是**简洁与健壮**：

1. **哨兵方案是最经典、最不易出错的环形队列实现**——满/空各是一个简单索引比较，逻辑一目了然；
2. **方案 C 必须妥善处理索引回绕（wrap）的边界**（一般要求容量是 2 的幂，或小心处理 `write` 绕一圈追上 `read` 的情形）。而 ipc-shm 的 `num_bufs` 是用户**任意配置**的整数（最多每 pool 4096、全通道 65534），不是 2 的幂，用差值判定会引入更多回绕 corner case；
3. 在跨核 volatile 共享内存上，一次读对方一个索引、做一个简单比较，比"读两个索引做减法再判边界"更稳。

## 类比：停车场牌子的故事（延续上次的类比）

**哨兵方案（方案 A）**：环形停车场 N+1 个车位，永远空一个位。入口闸机只看"出口闸机在哪"，出口闸机只看"入口闸机在哪"，**互相只看对方的闸机，从不去碰同一个东西** → 天然无锁、零冲突。

**count 方案（方案 B）**：把 N 个车位全用上，但在门口挂一块"剩余车位计数牌"。**进一辆车、出一辆车都要去翻同一块牌**，两个人会抢这块牌 → 要么排队（锁），要么用"原子翻牌机"（原子操作，仍有硬件依赖和争抢）。

**差值方案（方案 C）**：不浪费车位，也不挂计数牌，改用"记每辆车进出的总序号，用序号差算剩余数"。它仍然互不干扰，但规则比"留个空位"复杂，序号绕圈时要小心算错。

---

## 最终回答

1. **可以不用哨兵**，常见替代是"count 计数"或"差值索引"。
2. **不用哨兵后还是不是 SPSC？** 是——SPSC 只是"单生产者单消费者"的拓扑，和容量判定方式无关。
3. **还是不是无锁？**
   - 换 **count 方案** → 不再无锁（要锁）或不再"零竞争无锁"（要原子操作，跨核有平台依赖、cache 争抢）；
   - 换 **差值索引方案** → 理论上仍可零竞争无锁，但引入回绕/2 的幂等复杂度。
4. **哨兵方案本质上是"用 1 个槽位的代价，换取满/空判定只需两个单写者索引的简单比较，从而得到最干净、跨核最可靠的零竞争无锁 SPSC"**。这正是 ipc-shm 在异构核共享内存场景下选它的原因。

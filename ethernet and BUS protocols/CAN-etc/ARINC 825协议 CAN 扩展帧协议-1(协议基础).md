### 思路-总体属于网络管理的划分
>对比 TCP/IP协议；
>分单播和广播/组播
>29扩展帧分组；从高位开始仲裁，提供0-7个优先级，让CAN硬件实现低优先级的屏蔽，避免占用总线带宽；同时个体NODE也会开启filter过滤掉不关系的仲裁域信息；
>不匹配的报文，在 CAN 控制器硬件层就被丢弃了，根本不会触发 CPU 中断。
>
>仲裁域如下所示，这是单播的协议构成；（LCC逻辑通信通道）为2/6; 单播与TCP很类似：destination ID + server ID， 实现具体的业务通信；
>实际飞机大多时候是广播模式，亦即：LCC为广播周期数据用 LCC=2/3。此时destination ID + server ID没鸡毛用，综合为DOC（数据实体码，指示某种类型）

### 心法：_**“三位路权先抢占（Prio），四位 LCC 做开关(报文分类)。广播中间看对象(DOC)，单播中间找目标。最后七位定来源。”**

### 你的专属心智模型：ARINC 825 的“四级解码漏斗”

为了让你形成稳定的、肌肉记忆般的心智模型，我们把这 29 个 bit 想象成一个“四级漏斗”。当你拿到一帧数据，按从高位到低位（从左到右）依次穿过这个漏斗：

  

#### 第一级漏斗：路权层 —— 【Priority】 (3 bit)

- **做什么：** 判断“有多紧急”。
    
      
    
- **心智映射：** 救护车警笛。
    
      
    
- **动作：** 硬件层面的物理冲突解决。如果是 `0`，所有人让路；如果是 `7`，慢慢排队。
    
      
    

#### 第二级漏斗：路由层 —— 【LCC 分流器】 (4 bit)

- **做什么：** `switch(LCC)`，决定下一级的解析法则。
    
      
    
- **心智映射：** 邮局的分拣中心。
    
      
    
- **动作：**
    
      
    - 走向左边：发现是 `LCC=2`，挂上“大喇叭广播”的牌子。
        
          
        
    - 走向右边：发现是 `LCC=4/6`，挂上“私密信件”的牌子。
        
          
        

#### 第三级漏斗：业务层 —— 【核心载荷】 (14 bit 变形体)

- **做什么：** 根据第二级的指示，读取具体业务。
    
      
    
- **心智映射：**
    
      
    - **左边（广播模式 DOC）：** 这是一个“公告牌”。这 14 位直接翻译成“这是什么数据”。例如 `DOC = 0x123` 对应“左发动机转速”。不关心是谁发给谁的，只关心数据内容。
        
          
        
    - **右边（P2P模式 Dest + Service）：** 这是一个“带收件人和分发科室的信封”。前 7 位核对 `Dest ID`（是我吗？不是就扔掉）；后 7 位核对 `Service ID`（是找升级程序的，还是找配置程序的？）。
        
          
        

#### 第四级漏斗：溯源层 —— 【Source ID】 (7 bit)

- **做什么：** 无论上面怎么变，最后 7 位永远是发件人署名。
    
      
    
- **心智映射：** 发件人地址。
    
      
    
- **动作：** 提取出来用于记录 Log、故障排查（哪块板子发疯了一直在报错），或者作为回复 P2P 响应时的 `Dest ID`。

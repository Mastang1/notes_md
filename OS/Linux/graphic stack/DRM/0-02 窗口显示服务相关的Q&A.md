### 问题 1：多窗口像素 Buffer 的存储位置、分配者与分配时机

在 Linux DRM/KMS + Wayland 架构下，多应用的像素 Buffer 采用“客户端本地渲染 + 共享内存句柄传递”的零拷贝模式。


#### 1. 存储在什么地方？

- **物理存储介质**：存储在系统主存（RAM）或 GPU 专用显存（VRAM）中。
    
      
    - 在嵌入式 SoC（如 Rockchip、NXP、Mali/Vivante GPU）上，内存采用 UMA（统一内存架构），Buffer 存储在系统 RAM 的 **CMA（Contiguous Memory Allocator，连续内存分配器）** 或由 **IOMMU/System-MMU** 管理的物理页框中。
        
          
        
    - 在 PC 独立显卡（Intel/AMD/Nvidia）上，Buffer 存储在显卡的 VRAM 或 GTT（Graphics Translation Table）映射区中。
        
          
        
- **内核抽象表示**：在内核 DRM 子系统中，这些 Buffer 被包装为 **GEM Object（Graphics Execution Manager）**；跨进程共享时，被导出为 **DMA-BUF 文件描述符（File Descriptor, `int fd`）**。
    
      
    

#### 2. 谁分配的？

- **分配者**：由 **Qt 应用进程（Client 侧）的用户态图形驱动（Mesa UMD / Vendor EGL 库）** 主动申请分配，**而不是由窗口合成器（Compositor）分配**。
    
      
    
- **分配链路**：
    
    Qt 应用 $\rightarrow$ EGL 库 (`eglCreateWindowSurface`) $\rightarrow$ Mesa GBM (`gbm_bo_create`) $\rightarrow$ 系统调用 `ioctl(/dev/dri/card0, DRM_IOCTL_***_CREATE_GEM)` $\rightarrow$ 内核 DRM 内存分配器（如 DRM GEM / CMA）。
    
      
    

#### 3. 什么时候分配的？

- **首次窗口创建/显示时**：当 `QWindow::setVisible(true)` 或 `QWindow::create()` 被触发，QPA 插件创建 `wl_egl_window` 并调用 `eglCreateWindowSurface()` 时，驱动会预先分配双缓冲区（Double Buffering）或三缓冲区（Front Buffer / Back Buffer）。
    
      
    
- **窗口尺寸变更（Resize）时**：当应用窗口大小发生变化，旧的 Buffer 被销毁，驱动按新宽高重新申请 GEM Buffer。
    
      
    
- Swap Buffers 轮换时：在离屏渲染或缓冲区轮转期间，如果 Buffer 队列不够用，Mesa UMD 会按需延迟动态分配新 BO（Buffer Object）。
    
      
    

### 问题 2：点击 Button 的 GPU 渲染过程与 Dirty 区域 Buffer Descriptor

#### 1. 点击 Button 更新 Window 的 GPU 渲染完整流程

```markdown
[用户点击] -> Qt 事件分发 -> QWidget::update() 标脏
    │
    ▼
[Qt RHI / GLES 渲染命令构建]
    │  1. Bind Back Buffer (FBO)
    │  2. glScissor(dirty_x, dirty_y, dirty_w, dirty_h) 裁剪
    │  3. 绘制渐变背景、图片纹理、光影与文本 (Draw Calls)
    ▼
[Mesa Driver / GPU UMD 命令打包]
    │  将 GL 指令编译为 GPU Command Stream (Ring Buffer 数据包)
    ▼
[Kernel KMD 下发] -> ioctl(DRM_IOCTL_PANFROST_SUBMIT / DRM_IOCTL_AMDGPU_CS)
    │
    ▼
[GPU 硬件执行] -> Shader Core / Rasterizer 渲染像素写入 Back Buffer (CMA/VRAM)
    │
    ▼
[eglSwapBuffers()] -> 导出 Back Buffer 为 DMA-BUF fd
    │
    ▼
[Wayland 协议提交] -> wl_surface.damage_buffer() + wl_surface.commit()
```

#### 2. Dirty 区域与 Buffer Descriptor 的数据结构组成

在 Wayland / EGL 体系中，**“Buffer 内存描述符”** 与 **“Dirty (Damage) 脏区域描述符”** 在协议和 C 语言数据结构上是分离管理的：

  

##### (1) Buffer Descriptor（Buffer 本身的内存描述符）

在应用向 Compositor 发送 Buffer 时，通过 `zwp_linux_dmabuf_v1` 协议传递，其底层 C 语言数据结构封装（如 `struct gbm_bo` 或内核 DMA-BUF 描述符）如下：

  

C

```c
// 1. DMA-BUF 跨进程共享句柄元数据（用于在 Compositor 侧重建内存映射）
struct linux_dmabuf_buffer_params {
    int32_t  fds[4];          // DMA-BUF 的文件描述符 (指向 CMA/VRAM 物理内存)
    uint32_t offsets[4];      // 各 YUV/RGB 平面在内存中的偏移字节数
    uint32_t strides[4];      // 图像每行像素占用的字节跨度 (Pitch/Stride)
    uint64_t modifiers[4];    // 硬件压缩格式修饰符 (如 DRM_FORMAT_MOD_ARM_AFBC)
    uint32_t width;          // 像素宽度 (例如 800)
    uint32_t height;         // 像素高度 (例如 600)
    uint32_t format;         // 四字符像素格式 (如 DRM_FORMAT_XRGB8888)
};
```

##### (2) Dirty Region Descriptor（脏区域描述符）

当 Button 变化时，Qt 仅标记变化区域。该 Dirty 区域通过 **`wl_surface.damage_buffer(x, y, w, h)`** 接口传递给 Compositor，在 Mesa/Wayland 内核态中表现为 **`pixman_region32_t`** 结构：

  

C

```c
// 2. 局部更新的 Dirty 区域（矩形边界描述符）
typedef struct pixman_box32 {
    int32_t x1, y1; // 脏区域左上角坐标 (相对于 Buffer 像素坐标系)
    int32_t x2, y2; // 脏区域右下角坐标
} pixman_box32_t;

typedef struct pixman_region32 {
    pixman_box32_t  extents; // 包含所有脏矩形的最小包围盒
    pixman_box32_data_t *data; // 包含多个离散脏矩形数组 (Rectangles Array)
} pixman_region32_t;
```

_作用_：EGL 扩展 `EGL_KHR_partial_update` 和 `eglSetDamageRegionKHR()` 允许 GPU 只重新渲染/合成该 Rect 区域内的像素，大幅降低 GPU 显存带宽消耗。

  

### 问题 3：窗口合成器的窗口管理数据结构与 Z-Order 层级判定

#### 1. 管理多应用多 Window 的核心数据结构：Scene Graph（场景树）与双向链表

合成器（如 Weston、KWin、Mutter、wlroots）在内部使用 **Scene Graph（场景树）** 结合 **侵入式双向循环链表（Intrusive Doubly Linked List）** 来管理所有应用窗口。

  

以通用合成器框架 `wlroots` / `Weston` 的底层 C 语言实现为例：

  

C

```c
// 合成器全局视图管理对象
struct wlr_scene {
    struct wlr_scene_tree tree; // 场景树根节点
};

// 场景树节点 (包含子节点或具体 View)
struct wlr_scene_node {
    enum wlr_scene_node_type type; // 节点类型: TREE, BUFFER, RECT
    struct wlr_scene_tree *parent;
    struct wl_list link;          // 挂载到父节点 children 链表的双向链表节点
    
    int x, y;                      // 相对父节点的逻辑坐标
    bool enabled;                  // 是否可见
};

// 代表一个具体的 QWindow 渲染视图 (Surface View)
struct wlr_scene_buffer {
    struct wlr_scene_node node;   // 继承基类 Node
    struct wlr_buffer *buffer;    // 关联客户端传来的 DMA-BUF 像素 Buffer
    pixman_region32_t damage;     // 该窗口的 Dirty 区域
};
```

```markdown
[wlr_scene_tree (Root)]
       │
       ├──> wl_list: [Node: Dock/Panel]  (Z-Order: Topmost)
       │
       ├──> wl_list: [Node: Window 2 (Qt App B)]
       │
       └──> wl_list: [Node: Window 1 (Qt App A)] (Z-Order: Bottom)
```

#### 2. 合成器如何知道并管理窗口的堆叠顺序（Z-Order）？

Wayland 协议本身**没有显式的 Z-Index 属性**。窗口的堆叠顺序完全由 Compositor 维护的链表节点顺序（Node Iteration Order）决定：

  

1. **链表位置即 Z-Order**：
    
    在 `wl_list`（双向链表）中，**排在链表尾部（Tail）的节点堆叠在最上层，排在链表头部（Head）的节点位于最底层**（也可以反向定义）。
    
      
    
2. **绘制/合成时的 Z-Order 渲染**：
    
    当合成器触发 Repaint 时，以 **Painter's Algorithm（画家算法）** 从头到尾遍历链表：
    
      
    - 先绘制链表头部的 Window 1（最背景）；
        
          
        
    - 再绘制 Window 2；
        
          
        
    - 最后绘制链表尾部的 Window 3（最前景/最上方）。
        
          
        
3. **输入焦点与置顶操作**：
    
      
    - 当用户点击 Window 1 时，合成器捕获到鼠标坐标；
        
          
        
    - 执行 **Hit-Testing（碰撞检测/点检测）**：从 Z-Order **最上层到最下层**反向遍历场景树节点，匹配点是否在 `x, y, w, h` 范围内；
        
          
        
    - 命中 Window 1 后，合成器执行 `wl_list_remove(&win1->link)` 和 `wl_list_insert(&scene->children, &win1->link)`，将 Window 1 **移动到链表尾部**，从而实现“窗口置顶”。
        
          
        

### 问题 4：按钮变化场景中的 GPU 封装指令与 GPU 指令集入门

在包含图片、明暗、渐变等元素的 Button 发生变化时，上层 API（OpenGL ES / Vulkan）会将其翻译为 GPU 驱动指令并提交给 GPU 硬件执行。

  

#### 1. 复杂 Button 渲染场景中，GPU 执行的封装指令序列

当 Button 触发重绘时，GPU 驱动（Mesa UMD）构建并在硬件执行的典型指令包（Command Packets）流程如下：

  

1. **State Setting Packets（状态配置指令）**：
    
      
    - `SET_VIEWPORT`：设置渲染视口范围。
        
          
        
    - `SET_SCISSOR_RECT`：**配置裁剪矩形为 Button 的 Dirty 区域**，GPU Rasterizer 将自动丢弃此矩形外的所有片元。
        
          
        
    - `SET_BLEND_ENABLE / SET_BLEND_FUNC`：开启 Alpha 混合，配置混合方程为 `SrcAlpha * Src + (1 - SrcAlpha) * Dst`，用于处理按钮的圆角抗锯齿和半透明阴影。
        
          
        
2. **Shader Program & Resource Binding Packets（着色器与资源绑定指令）**：
    
      
    - `BIND_PIPELINE / BIND_PROGRAM`：加载针对该 Button 编译好的 Vertex Shader（顶点着色器）与 Fragment Shader（片元着色器）。
        
          
        
    - `BIND_TEXTURE`：绑定 Button 的贴图资源（如按钮图标图片、阴影 Texture Map）。
        
          
        
    - `BIND_UNIFORM_BUFFER`：上传 Uniform 变量（如渐变起始颜色 `ColorA`、终止颜色 `ColorB`、光影方向向量）。
        
          
        
3. **Primitive Draw Call Packets（图元绘制指令）**：
    
      
    - `DRAW_INDEXED (Primitive: TRIANGLE_STRIP, Count: 6)`：下发绘制指令，将 Button 拆分为 2 个三角形（4 个顶点组成的矩形），触发 GPU 几何管线。
        
          
        
4. **Flush & Barrier Packets（同步与刷盘指令）**：
    
      
    - `TEXTURE_BARRIER / MEMORY_BARRIER`：确保 Shader 写入 Tile Buffer/显存的像素数据完成，避免数据竞争。
        
          
        
    - `TILE_STORE / RESOLVE_FRAMEBUFFER`：（在 ARM Mali / PowerVR 等 Tile-Based GPU 上）将 Tile Buffer 中的最终渲染结果刷入外存（RAM/VRAM 中的 Back Buffer）。
        
          
        

#### 2. GPU 支持的底层指令集架构（GPU ISA & Command Interface）基础普及

要理解 GPU 的指令系统，需要区分 **GPU 命令流（Command Streamer 指令）** 与 **GPU 执行核心指令（Shader ISA）**：

  

```
+-----------------------------------------------------------------------+
|  1. GPU 命令流指令 (Command Streamer Packets - 由 CP/Front-End 解析) |
|  控制流、寄存器配置、DMA 搬运、Draw Call 发起                         |
+-----------------------------------------------------------------------+
                                   │
                                   ▼
+-----------------------------------------------------------------------+
|  2. Shader Core 核心指令 (GPU ISA - 由 ALU/Vector Core 执行)          |
|  向量算术运算、采样指令、流控制、像素导出                              |
+-----------------------------------------------------------------------+
```

##### (1) 控制驱动层的 GPU 命令流指令（Command Streamer / CP Packets）

这类指令由 GPU 前端硬件（Command Processor）读取，用于控制 GPU 的管线状态和任务调度：

  

- **寄存器配置指令（Write Register Packets）**：直接向 GPU 内部硬件寄存器写入配置（如设置 Framebuffer 地址、格式、Z-Buffer 模式）。
    
      
    
- **DMA/Copy 指令（DMA/Engine Transfer）**：驱动指挥 GPU 内部 DMA 引擎在显存间快速拷贝数据（如 `vkCmdCopyBuffer`）。
    
      
    
- **同步与Fence指令（Wait/Signal Events）**：控制 GPU 内部多个 Shader 核心之间的同步，或者与 CPU 进行完成状态同步。
    
      
    

##### (2) 渲染执行层的 GPU 硬件指令集（Shader ISA - Microcode）

GPU 的核心（Shader Core）本质上是高度并行的 **SIMD（单指令多数据）/ SIMT（单指令多线程）** 处理器。其 ISA 指令主要分为以下几类：

  

|**指令类别**|**常见硬件指令示例**|**指令功能与在 Button 场景中的应用**|
|---|---|---|
|算术运算指令<br><br>  <br>  <br><br>(ALU Ops)|`FADD` (Float Add)<br><br>  <br>  <br><br>`FMUL` (Float Mul)<br><br>  <br>  <br><br>**`FFMA` / `MAD`** (Fused Multiply-Add)|**GPU 极其擅长乘加运算**。`FFMA` 在单周期内完成 $a \times b + c$。<br><br>  <br>  <br><br>用于计算按钮的渐变色线性插值（`lerp`）、光影衰减方程。|
|纹理采样指令<br><br>  <br>  <br><br>(Texture Fetch)|`TEX` / `SAMPLE`<br><br>  <br>  <br><br>`SAMPLE_B` (Lod bias)<br><br>  <br>  <br><br>`GATHER`|**由 TPU（纹理处理单元）硬件加速**。<br><br>  <br>  <br><br>根据 UV 坐标在按钮图标图片中提取像素值，并自动完成双线性过滤（Bilinear Interpolation）。|
|向量与矩阵指令<br><br>  <br>  <br><br>(Vector Ops)|`DP3` / `DP4` (Dot Product)<br><br>  <br>  <br><br>`VEC4_ADD`|计算两个向量的点积。用于光影计算，求光照方向与按钮表面法线的夹角。|
|插值与几何指令<br><br>  <br>  <br><br>(Attribute Fetch)|`VARYING_INTERP`<br><br>  <br>  <br><br>`ROUND` / `FLOOR`|在光栅化阶段，自动将顶点着色器的输出（如坐标、UV）在像素点之间进行重心坐标插值。|
|逻辑与流控制<br><br>  <br>  <br><br>(Control Flow)|`CMP` (Compare)<br><br>  <br>  <br><br>`BRANCH` / `IF` / `ELSE`<br><br>  <br>  <br><br>`DISCARD`|比较与跳转指令。<br><br>  <br>  <br><br>在 Fragment Shader 中，用于判断当前像素是否超出了按钮圆角半径，若超出则执行 `DISCARD` 丢弃该像素。|
|像素导出指令<br><br>  <br>  <br><br>(Pixel Export / ROP)|`EXPORT_COLOR`<br><br>  <br>  <br><br>`TILE_STORE`|将 Fragment Shader 计算出的最终 RGBA 颜色值写入 Framebuffer，或写回 Tile-Buffer（TBR 架构）。|

#### 总结概括

整个过程可以简述为：

Qt 通过改变逻辑数据控制图形 Pipeline；Mesa 驱动将界面元素拆解为几何与像素指令并绑定脏区域；Wayland Compositor 利用链表 Scene Graph 管理各窗口 Z-Order 并通过 DMA-BUF 句柄进行零拷贝聚合；最后 GPU 硬件在指令流与 Shader ISA 的协作下，仅对 Button 变动的矩形区域进行并行像素渲染，最终将结果通过 DRM/KMS 刷往屏幕。

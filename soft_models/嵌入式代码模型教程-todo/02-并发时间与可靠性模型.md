## 模型 5：ISR 上半部 + 延后工作下半部

**优先级：P0｜层次：HAL / Driver / OS**

### 第一性原理

中断的不可消除约束是：它打断了正常执行，通常优先级高、栈小、可调用 API 受限。中断占用时间越长，其他中断的最坏延迟越大。

因此把处理拆成两部分：

- 上半部只完成“阻止数据丢失、确认硬件、记录事实、唤醒后续”；
- 下半部在线程或工作队列中做解析、日志、内存分配和业务回调。

### 费曼解释

火警接线员先记录地址并立即派车，不在电话里调查起火原因。ISR 是接线员；工作队列是到现场的消防队。

### 核心不变量

- ISR 工作量有固定上界；
- 清除/确认中断的顺序符合硬件手册；
- ISR 与下半部之间的数据在发布前已经写完；
- 同一工作项是否允许重复入队必须明确；
- 下半部不能假设每次 IRQ 对应一次工作项，必要时用计数器或状态位合并。

### 核心场景

~~~mermaid
sequenceDiagram
    participant HW as "UART/DMA"
    participant ISR as "上半部 ISR"
    participant Q as "工作队列"
    participant W as "下半部 Worker"
    HW->>ISR: IRQ
    ISR->>HW: 读状态/清 IRQ
    ISR->>Q: submit(rx_work)
    ISR-->>HW: 快速返回
    Q->>W: 调度工作项
    W->>W: 解析、协议处理、回调
~~~

### 最小 Demo（C11，裸机轮询模拟下半部）

~~~c
#include <stdatomic.h>
#include <stdbool.h>
#include <stdio.h>

static atomic_bool rx_pending;
static atomic_uint irq_count;

void uart_isr(void) {
    /* hw_ack_irq(); hw_read_fifo_to_dma_or_ring(); */
    atomic_fetch_add_explicit(&irq_count, 1u, memory_order_relaxed);
    atomic_store_explicit(&rx_pending, true, memory_order_release);
}

void worker_poll(void) {
    if (!atomic_exchange_explicit(&rx_pending, false,
                                  memory_order_acquire)) {
        return;
    }
    unsigned n = atomic_exchange_explicit(&irq_count, 0u,
                                          memory_order_relaxed);
    printf("deferred processing for %u IRQ(s)\n", n);
}

int main(void) {
    uart_isr();
    uart_isr();       /* 合并唤醒，但计数不丢 */
    worker_poll();
}
~~~

### 何时不用与误用

- 只有读取一个寄存器并置位即可完成时，不必另建线程；
- 工作项内阻塞会拖住共享系统工作队列，必要时用专用队列；
- 只用布尔 pending 合并事件时，若次数有语义会丢计数；
- 不要从 ISR 调用普通阻塞队列 API，要用明确的 FromISR/ISR-safe 入口。

## 模型 6：有界队列 + 明确反压

**优先级：P0｜层次：OS / Library / User App**

### 第一性原理

若长期平均到达率 λ 大于处理率 μ，任何有限内存最终都会满；把队列做大只推迟失败。物理 RAM 有界，所以系统必须在“满”发生前选定策略：

- 阻塞生产者；
- 拒绝新数据；
- 覆盖最旧数据；
- 合并同类事件；
- 降采样/降级；
- 向上游发出暂停或窗口缩小信号。

反压不是队列的附加功能，而是有界系统在过载时的定义。

### 费曼解释

水池进水比排水快时，换大水池不能解决永久问题。必须关小进水阀、让水溢到安全区，或主动丢掉不重要的水。那个预先约定的动作就是反压策略。

### 核心场景

~~~mermaid
sequenceDiagram
    participant P as "Producer"
    participant Q as "Bounded Queue"
    participant C as "Consumer"
    P->>Q: push(item)
    alt 队列有空间
        Q-->>P: ACCEPTED
        C->>Q: pop()
    else 队列已满
        Q-->>P: FULL
        P->>P: drop / coalesce / pause source
    end
~~~

### 最小 Demo（C11，丢弃新样本并计数）

~~~c
#include <stdbool.h>
#include <stdio.h>

#define CAP 4u
static int q[CAP];
static unsigned head, tail, used, dropped;

static bool try_push(int value) {
    if (used == CAP) {
        dropped++;
        return false;
    }
    q[head] = value;
    head = (head + 1u) % CAP;
    used++;
    return true;
}

static bool try_pop(int *value) {
    if (used == 0u) return false;
    *value = q[tail];
    tail = (tail + 1u) % CAP;
    used--;
    return true;
}

int main(void) {
    int value;
    for (int i = 0; i < 6; ++i) (void)try_push(i);
    while (try_pop(&value)) printf("%d ", value);
    printf("\ndropped=%u\n", dropped);
}
~~~

### 选择策略

| 数据语义 | 推荐满策略 |
|---|---|
| 控制命令、告警 | 拒绝并显式上报；通常不能静默覆盖 |
| 传感器最新值 | 覆盖最旧或只保留最新 |
| 可合并刷新事件 | 合并为一个 pending 位 |
| 网络/串口流 | 协议流控、窗口或暂停 DMA/接收 |
| 日志 | 按等级丢弃、统计丢失量 |

### 常见误用

- 队列满时无限等待，造成优先级反转或环路死锁；
- 静默丢包而无 dropped/high-watermark 指标；
- 高优先级消费者被低优先级锁持有者阻塞；
- 用队列长度掩盖持续吞吐不足。

- [Linux kfifo](https://docs.kernel.org/core-api/kernel-api.html#kfifo-interface)

## 模型 7：截止时间 + 有界重试 + 退避抖动

**优先级：P0｜层次：Driver / Library / User App**

### 第一性原理

外设和链路存在瞬态故障；一次失败就放弃会降低可用性，无限重试又会把暂时故障变成永久占用。正确问题不是“等多久一次”，而是“整个操作还剩多少预算”。

设总截止时间 D、单次尝试上界 T、重试间隔 B。每次尝试前检查剩余预算，只允许在剩余时间足够时继续。指数退避减少持续施压，随机抖动避免多个设备同步重试形成重试风暴。

### 费曼解释

打电话没人接，可以晚点再拨，但你还有一班飞机。你不会每次都重新给自己“再等五分钟”，而是看离登机还剩多少时间；人群也不要整点同时拨号，所以每个人随机错开一点。

### 核心不变量

- 使用单调时钟计算 elapsed/deadline；
- 重试次数和总时长都有上界；
- 只重试可恢复错误；
- 非幂等操作重试前必须有请求 ID、查询状态或补偿动作；
- 退避有最大值，抖动范围明确。

### 核心场景

~~~mermaid
sequenceDiagram
    participant A as "Application"
    participant R as "Retry Controller"
    participant D as "Device/Network"
    A->>R: execute(deadline)
    loop 尚有预算且错误可重试
        R->>D: attempt()
        D-->>R: transient error
        R->>R: backoff + jitter
    end
    alt 成功
        R-->>A: OK
    else 截止时间耗尽
        R-->>A: TIMEOUT
    end
~~~

### 最小 Demo（C11）

~~~c
#include <stdint.h>
#include <stdio.h>

typedef enum { IO_OK, IO_BUSY, IO_FATAL } io_result_t;

static io_result_t fake_io(unsigned attempt) {
    return (attempt < 3u) ? IO_BUSY : IO_OK;
}

static uint32_t full_jitter(uint32_t cap_ms, uint32_t random32) {
    return (cap_ms == 0u) ? 0u : random32 % (cap_ms + 1u);
}

static io_result_t run_with_budget(uint32_t budget_ms) {
    uint32_t elapsed = 0u;
    uint32_t backoff = 10u;
    uint32_t rng = 0x12345678u;

    for (unsigned attempt = 1u; attempt <= 5u; ++attempt) {
        io_result_t r = fake_io(attempt);
        if (r == IO_OK || r == IO_FATAL) return r;

        rng = rng * 1664525u + 1013904223u;
        uint32_t wait = full_jitter(backoff, rng);
        if (elapsed + wait >= budget_ms) break;
        elapsed += wait;       /* MCU 上替换为基于单调时钟的等待 */
        if (backoff < 160u) backoff *= 2u;
    }
    return IO_BUSY;
}

int main(void) {
    printf("result=%d\n", run_with_budget(500u));
}
~~~

### 常见误用

- 每层都独立重试，导致尝试次数相乘；
- 把校验失败、权限失败等永久错误当瞬态错误；
- 只限制单次超时，不限制总截止时间；
- 重发写命令却没有幂等键，导致重复扣款、重复写 Flash 或重复启动电机。

## 模型 8：任务心跳 + 总闸看门狗

**优先级：P1｜层次：OS / User App**

### 第一性原理

主循环能喂硬件狗，不代表每个关键任务都在前进。若任意上下文都能直接喂狗，一个卡死任务会被健康任务掩盖。

正确结构是两级证明：

1. 每个关键任务在完成一个有意义的进度点后置位自己的 epoch/heartbeat；
2. 监督者只在所有必需任务都前进且系统健康时喂硬件狗。

看门狗是最后恢复手段；复位前还要保存 reset reason、最后进度和错误上下文。

### 费曼解释

老师不是看“教室里有人说话”就认定全班到齐，而是逐个点名。只有所有必须到场的人都答到，才在总表上盖章。硬件狗只认这枚总章。

### 核心场景

~~~mermaid
sequenceDiagram
    participant T1 as "Task A"
    participant T2 as "Task B"
    participant S as "Supervisor"
    participant W as "Hardware WDT"
    T1->>S: heartbeat(A, epoch++)
    T2->>S: heartbeat(B, epoch++)
    S->>S: 检查所有任务均前进
    alt 全部健康
        S->>W: feed()
    else 任一任务停滞
        S->>S: 保存诊断信息
        Note over W: 到期复位
    end
~~~

### 最小 Demo（C11）

~~~c
#include <stdbool.h>
#include <stdint.h>
#include <stdio.h>

#define TASKS 3u
static uint32_t epoch[TASKS];
static uint32_t seen[TASKS];

static void task_progress(unsigned id) {
    if (id < TASKS) epoch[id]++;
}

static bool supervisor_may_feed(void) {
    bool all_advanced = true;
    for (unsigned i = 0; i < TASKS; ++i) {
        if (epoch[i] == seen[i]) all_advanced = false;
    }
    if (all_advanced) {
        for (unsigned i = 0; i < TASKS; ++i) seen[i] = epoch[i];
    }
    return all_advanced;
}

int main(void) {
    task_progress(0); task_progress(1); task_progress(2);
    puts(supervisor_may_feed() ? "feed WDT" : "do not feed");
    task_progress(0); task_progress(2); /* task 1 卡住 */
    puts(supervisor_may_feed() ? "feed WDT" : "do not feed");
}
~~~

### 常见误用

- 在定时中断中无条件喂狗；
- 心跳只表示任务被调度过，而不是完成了有效进度；
- 长合法操作未设计临时租约/阶段性进度；
- 调试版本永久禁用看门狗，导致问题只在发布版出现；
- 复位后不记录 reset reason，现场只剩“设备重启了”。

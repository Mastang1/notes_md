# 控制流与状态模型

返回总览：[[00-嵌入式代码模型学习地图]]

## 模型 1：有限状态机（FSM）

**优先级：P0｜层次：Driver / User App**

### 第一性原理

如果同一个事件在“空闲、运行、故障”时含义不同，那么系统的输出不仅由输入决定，还由历史决定。历史不可能靠猜，必须压缩成一个显式状态：

\[
next\_state,\ action = F(current\_state,\ event)
\]

因此 FSM 不是为了画图，而是把“隐藏在调用顺序和布尔变量里的历史”变成可枚举、可审查的数据。

### 费曼解释

把设备想成一扇自动门。门收到“开门”请求时，如果正关闭，应该反向；如果已经打开，不必再次启动电机；如果故障，应拒绝动作。按钮没有变，变化的是门“现在在哪一种处境”。FSM 就是一张“处境 + 事件 → 下一步”的表。

### 核心不变量

- 任一时刻恰好处于一个状态；
- 每个被接受的事件最多引发一次转换；
- entry/exit 动作只在跨越状态边界时执行；
- 未定义事件必须显式忽略、上报或进入故障，不能落入偶然路径。

### 核心场景

~~~mermaid
sequenceDiagram
    participant E as "事件源"
    participant F as "FSM"
    participant H as "硬件"
    E->>F: START
    Note over F: IDLE -> RUNNING
    F->>H: motor_on()
    E->>F: FAULT
    Note over F: RUNNING -> ERROR
    F->>H: motor_off()
    E->>F: RESET
    Note over F: ERROR -> IDLE
~~~

### 最小 Demo（C11）

~~~c
#include <assert.h>
#include <stdio.h>

typedef enum { ST_IDLE, ST_RUNNING, ST_ERROR } state_t;
typedef enum { EV_START, EV_STOP, EV_FAULT, EV_RESET } event_t;

typedef struct {
    state_t state;
    int motor_on;
} machine_t;

static void dispatch(machine_t *m, event_t e) {
    assert(m != NULL);
    switch (m->state) {
    case ST_IDLE:
        if (e == EV_START) {
            m->motor_on = 1;
            m->state = ST_RUNNING;
        } else if (e == EV_FAULT) {
            m->state = ST_ERROR;
        }
        break;
    case ST_RUNNING:
        if (e == EV_STOP) {
            m->motor_on = 0;
            m->state = ST_IDLE;
        } else if (e == EV_FAULT) {
            m->motor_on = 0;
            m->state = ST_ERROR;
        }
        break;
    case ST_ERROR:
        if (e == EV_RESET) {
            m->state = ST_IDLE;
        }
        break;
    default:
        assert(!"invalid state");
    }
}

int main(void) {
    machine_t m = { .state = ST_IDLE };
    dispatch(&m, EV_START);
    dispatch(&m, EV_FAULT);
    dispatch(&m, EV_RESET);
    printf("state=%d motor=%d\n", m.state, m.motor_on);
}
~~~

### 何时不用

- 完全无历史的纯函数；
- 只有一个线性动作、没有异步事件；
- 状态组合正交且数量爆炸时，不要硬做笛卡尔积，考虑多个协作 FSM 或 HSM。

### 常见误用

- 用十几个布尔量组合出隐式状态；
- 在状态处理函数里阻塞，导致后续事件无法处理；
- 转换前先改状态、动作失败后却没有回滚；
- 把“错误码”与“生命周期状态”混为一谈。

## 模型 2：事件循环与 Run-to-Completion

**优先级：P1｜层次：OS / Library / User App**

### 第一性原理

共享可变状态之所以难，是因为多个执行上下文能在任意语句间穿插。若把所有修改状态的动作变成短事件，并由单一执行上下文逐个处理，那么处理一个事件期间没有别的事件插入，状态天然串行化。

代价也直接来自原理：单个 handler 的最坏执行时间决定了整个循环的响应上界，所以 handler 必须短、非阻塞。

### 费曼解释

像只有一个窗口的办事大厅：所有人拿号排队，窗口一次办完一件短业务。好处是不用担心两个工作人员同时改同一份档案；坏处是某个人如果占着窗口打长电话，后面所有人都被拖住。

### 核心不变量

- 状态只在事件循环上下文写；
- handler 必须 run-to-completion，不在中间等待外部资源；
- 慢操作拆成“发起 → 完成事件”；
- 队列必须有界，并有过载策略。

### 核心场景

~~~mermaid
sequenceDiagram
    participant I as "IRQ/生产者"
    participant Q as "有界事件队列"
    participant L as "事件循环"
    participant S as "模块状态"
    I->>Q: post(EV_RX)
    L->>Q: pop()
    Q-->>L: EV_RX
    L->>S: handler(EV_RX)
    Note over L,S: 执行期间不处理下一事件
    L->>Q: pop()
~~~

### 最小 Demo（C11）

~~~c
#include <stdbool.h>
#include <stdint.h>
#include <stdio.h>

typedef enum { EV_TICK, EV_BUTTON, EV_IO_DONE } event_t;
#define QCAP 8u

static event_t q[QCAP];
static unsigned rd, wr, used;
static unsigned led;

static bool post(event_t e) {
    if (used == QCAP) return false;
    q[wr] = e;
    wr = (wr + 1u) % QCAP;
    used++;
    return true;
}

static bool take(event_t *e) {
    if (used == 0u) return false;
    *e = q[rd];
    rd = (rd + 1u) % QCAP;
    used--;
    return true;
}

static void handle(event_t e) {
    switch (e) {
    case EV_BUTTON:  led ^= 1u; break;
    case EV_TICK:    break;
    case EV_IO_DONE: puts("I/O complete"); break;
    }
}

int main(void) {
    event_t e;
    post(EV_BUTTON);
    post(EV_IO_DONE);
    while (take(&e)) handle(e);
    printf("led=%u\n", led);
}
~~~

### 何时不用

- handler 必须进行不可拆分的长阻塞调用；
- 硬实时任务需要抢占低优先级工作；
- 多核高吞吐场景需要真正并行。

## 模型 3：表驱动分派

**优先级：P1｜层次：Driver / Protocol / Library**

### 第一性原理

一个长分支同时编码了“键 → 行为”的映射和每个行为的实现。把映射提升为数据表后，查找机制稳定，新增命令只新增一行。真正的不变量变为：键唯一、参数长度先验证、处理函数遵循同一契约。

### 费曼解释

餐馆不是让前台背下“菜号 37 要找哪位厨师”，而是查菜单：菜号、最低原料、负责厨师都在一行。表驱动就是把不断增长的分支写成可检查的菜单。

### 核心场景

~~~mermaid
sequenceDiagram
    participant RX as "协议接收"
    participant D as "Dispatcher"
    participant T as "命令表"
    participant H as "Handler"
    RX->>D: opcode, payload, length
    D->>T: find(opcode)
    T-->>D: min_len, handler
    alt 长度合法
        D->>H: handler(payload)
    else 非法
        D-->>RX: ERR_BAD_LENGTH
    end
~~~

### 最小 Demo（C11）

~~~c
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

typedef int (*handler_fn)(const uint8_t *, size_t);
typedef struct { uint8_t opcode; size_t min_len; handler_fn fn; } command_t;

static int ping(const uint8_t *p, size_t n) { (void)p; (void)n; return 0; }
static int set_led(const uint8_t *p, size_t n) {
    if (n < 1u) return -1;
    printf("led=%u\n", p[0] != 0u);
    return 0;
}

static const command_t commands[] = {
    { 0x01u, 0u, ping },
    { 0x10u, 1u, set_led },
};

static int dispatch(uint8_t op, const uint8_t *p, size_t n) {
    for (size_t i = 0; i < sizeof commands / sizeof commands[0]; ++i) {
        if (commands[i].opcode == op) {
            if (n < commands[i].min_len) return -2;
            return commands[i].fn(p, n);
        }
    }
    return -3;
}

int main(void) {
    const uint8_t on[] = {1u};
    return dispatch(0x10u, on, sizeof on);
}
~~~

### 适用边界与误用

- 适合命令、寄存器、状态转换、编解码器映射；
- 表很小时线性查找最简单；规模大再用排序/二分或直接索引；
- 不要把任意外部 opcode 直接当数组下标；
- 不要遗漏长度、权限、当前状态等前置条件；
- 复杂策略不要塞进巨大表格，表只负责稳定映射。

## 模型 4：层次状态机（HSM）

**优先级：P1｜层次：User App Framework**

### 第一性原理

普通 FSM 中，多个子状态常重复处理 STOP、TIMEOUT、FAULT。重复说明这些状态共享一个更高层语义。HSM 把共同处理放进父状态：子状态先尝试处理，未处理事件逐层向父状态冒泡。

它解决的是状态行为的复用，不是让状态图无限嵌套。

### 费曼解释

“在公司里，员工先按小组规则处理问题；小组没规则，就交给部门；部门也没有，再交给公司总则。” FAULT 可以在“运行中”的父状态统一停机，不必在“预热、加速、恒速”里各复制一遍。

### 核心场景

~~~mermaid
stateDiagram-v2
    [*] --> Off
    Off --> Running: START
    state Running {
        [*] --> Warmup
        Warmup --> Steady: READY
        Steady --> Warmup: RECONFIGURE
    }
    Running --> Error: FAULT（父状态统一处理）
    Running --> Off: STOP（父状态统一处理）
    Error --> Off: RESET
~~~

### 最小 Demo（C11）

~~~c
#include <stdbool.h>
#include <stdio.h>

typedef enum { S_OFF, S_WARMUP, S_STEADY, S_ERROR } state_t;
typedef enum { E_START, E_READY, E_STOP, E_FAULT, E_RESET } event_t;

static bool running_parent(state_t *s, event_t e) {
    if (e == E_STOP)  { *s = S_OFF;   return true; }
    if (e == E_FAULT) { *s = S_ERROR; return true; }
    return false;
}

static void dispatch(state_t *s, event_t e) {
    switch (*s) {
    case S_OFF:
        if (e == E_START) *s = S_WARMUP;
        break;
    case S_WARMUP:
        if (e == E_READY) *s = S_STEADY;
        else (void)running_parent(s, e);
        break;
    case S_STEADY:
        (void)running_parent(s, e);
        break;
    case S_ERROR:
        if (e == E_RESET) *s = S_OFF;
        break;
    }
}

int main(void) {
    state_t s = S_OFF;
    dispatch(&s, E_START);
    dispatch(&s, E_FAULT);
    printf("state=%d\n", s);
}
~~~

### 何时不用

- 三四个状态且没有重复行为时，普通 FSM 更直白；
- 如果正交区域很多，考虑多个协作状态机；
- 如果事件处理会阻塞，先解决执行模型，HSM 不能修复阻塞。
